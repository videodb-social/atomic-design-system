Text contracts (accessibility-tested floors)

  • Body on dark: minimum white at 75% (primary) or 65% (utility).
  • Body on light: minimum #111 at 75% (primary) or 60% (utility).
  • Display headings can sit at 90–95% opacity.
  • Decorative chrome (dot patterns, hairlines, fade gradients): 25–35% — never for readable glyphs.
  • Brand orange on body text fails AA. Never use orange for body — accent surfaces and CTAs only.

Usage

Read from tokens; never use raw hex in markup or component CSS. Surface flips work because every component binds to scoped variables that rebind under .bk-section--dark / .bk-section--light / .is-flipped-*.

Atoms / Button

Button

Pill-shaped action triggers. One primary per viewport; secondary and ghost handle paired CTAs and tertiary actions. All variants share label-md text, 9999px radius, and 44px minimum touch target. Stateful variants (disabled, loading) and editorial variants (arrow-circle CTA, anchor pill) live on this page too.

Usage rules

One primary per viewport. Two primaries in the same screen competing for attention dilutes the orange.

Pill always. All buttons use 9999px radius. No exceptions — never a hard-cornered button.

Min 44px touch target. Below 44×44 fails WCAG 2.5.5 on touch devices. Icon-only buttons hit this via ::after expansion.

Disabled needs explanation. Never ship a dead button with no context — pair it with helper text or a tooltip so the user knows why it can't be clicked.

Loading blocks double-submit. The async pattern is aria-busy="true" + disabled together, so neither pointer nor keyboard can re-fire the action.

Three layers — backdrop (full-viewport blur + dim), dialog box (charcoal/white, 16px radius, soft lift), close affordance (white circle below the modal, visible and reachable). Usage rules

Three intent variants only. CTA drives a decision; Info acknowledges a state; Form captures input. Don't invent a fourth — if you need something else, you're using a modal where a page or inline disclosure belongs.

Close affordance lives outside the modal. The white circle below the dialog is intentional — it's reachable on touch (away from the modal's edge) and reads as a discrete affordance, not chrome. Esc + backdrop click also close.

Body-scroll-lock on open. The page underneath shouldn't scroll while the modal is open. Production code adds overflow: hidden to <body> and restores on close.

Focus management. First focusable input receives focus ~100ms after open (so the open animation finishes first). On close, focus returns to the trigger element.

Composed from atoms + molecules. Button for the action pair, Input + Field label for the form variant, Form field for multi-field arrangements.

Layout

1400 px frame, five canonical breakpoints, two-tier column offset. A centred 1400px column with 1px vertical hairlines on either side, persisting through every section. Sections alternate dark ↔ light, full commitment per section.

Column offset — two-tier rule

Strict 2/10 at the section opener; large interactives can opt-in to .full-bleed-content inside the right column.

Section-opener tier (default)

Every section, light or dark: section code in left col (md:col-span-3 lg:col-span-2), content in right col (md:col-span-9 lg:col-span-10 max-w-5xl). Heading + lead use 8/4 split inside the right column.

Inside the right column, large interactive containers MAY fill the full 10-column width via the .full-bleed-content modifier. Applies to: code blocks, hero feature surfaces, lifecycle flows, comparison tables wider than 8/4, pricing tier finder, carousels, tickers.

Scroll reveal · system-wide entrance pattern

One sanctioned scroll-triggered entrance animation for the entire system. Elements with data-ds-reveal (or auto-decorated targets like .ds-section-heading and .ds-hero) fade + translate from 12px below their resting position to in-place when they enter the viewport at 12% threshold. One-shot per element — once revealed, stays revealed; no re-trigger on scroll-back-up. prefers-reduced-motion: reduce skips the animation entirely.

Auto-decorated targets

On every page activation, decorateReveals() auto-adds data-ds-reveal to these classes — designers never need to mark them manually:

SelectorWhy
.ds-section-headingSection headings always benefit from a reveal moment — the entire section-heading molecule (eyebrow + h2 + lead) fades in as one unit.
.ds-heroThe hero wrapper reveals as one block: display + lead + CTA pair all in. No staggered chrome, no slideshow feel.

Opt-in usage

For elements outside the auto-targets, add the attribute explicitly. Use data-ds-reveal-delay in 80ms increments for sequenced reveals — typically a 3- or 4-up card grid:

<div class="ds-card-grid">
  <article data-ds-reveal data-ds-reveal-delay="0">...</article>
  <article data-ds-reveal data-ds-reveal-delay="80">...</article>
  <article data-ds-reveal data-ds-reveal-delay="160">...</article>
</div>

Rules

Don't decorate everything. Headlines, heroes, top-level cards in grids, big-stats blocks, hero displays. Body paragraphs, list items, button labels, table rows — never. Aggressive reveal-everywhere is the antipattern this primitive is designed to prevent.

One direction only. Always fade + translateY upward. No mixing slide-left, slide-right, scale, rotate in the same system. One primitive, one mental model.

One-shot. Observer unobserves after first reveal. Scrolling back up doesn't re-trigger — preventing the "slideshow site" antipattern.

Stagger sparingly. Reach for data-ds-reveal-delay only when the elements form a parallel set (3-up cards, 4-up stats). Don't stagger arbitrary adjacent elements. Cap stagger sequences at 4 — beyond that, the last element waits noticeably long.

Always honors reduced-motion. CSS media query forces the element to its final state with no transition. JS doesn't need to know.

Iconography

Solar via Iconify. Linear weight by default. Bold for emphasis. All icons in the system come from the Solar collection via the Iconify CDN — no SVGs in the repo. Icons inherit text color; the brand orange is reserved for surfaces and active states.

Rules

  • One icon family. Solar only. No mixing with Phosphor, Heroicons, Lucide, etc.

Brand & voice

Infrastructure-confident, editorial, declarative. The voice reads like an engineer wrote it for other engineers, but it was edited by someone who reads The Economist.

Tone

  • No exclamation marks. No emoji. Anywhere. Period.
  • Sentence case for everything readable (display headings, body, list items, card titles). Title Case is reserved for two places: section labels in the nav ("Platform", "Agents", "Pricing"), and product / tier names ("Free", "Usage-Based", "Committed Annual").

  • Second person for product-facing copy ("you", "your"). Never "we" except in the footer.
  • Active voice. Always "the agent searches", never "is being processed by".

Lexicon — use these words

infrastructure-grade, scaffolding, layer, primitive, queryable, multimodal, runtime, native, scaled, deterministic, programmatic, perception layer, agentic, index, embed, ingest.

Lexicon — never use

seamlessly, magical, unlock, supercharge, revolutionary, world-class, cutting-edge, AI-powered, leverage, robust, enterprise-grade. These read as marketing pap. The VideoDB voice is technical confidence; these words signal absence of confidence.

Microcopy patterns

  • Button labels: sentence-case Geist label-md 14 / 400 / 20px. One word ideally — "Subscribe", "Get access", "Notify me". Two if needed. Never uppercase mono.

Motion / Particle dome

Particle dome

The brand-signature ambient animation. A 15,000-particle (production) or 5,000-particle (this preview) point cloud arranged as a hemispherical dome that breathes — size oscillates with inverse-coupled per-vertex distortion, plus multi-axis rotation drifting between dominant axes. Renders to a WebGL canvas via Three.js (r128, dynamically loaded on first appearance, ~150 KB gzipped, cached after first load). Dark-only at v1 (additive blending of white particles depends on a dark backdrop). Respects prefers-reduced-motion: reduce — animation halts and the dome holds at the starting frame. Pauses when scrolled offscreen via IntersectionObserver to spare GPU.

Variants

Single variant at v1 — the breathing dome. Two presets: data-ds-particle-scale="preview" (5,000 points, smaller radius, for docs / contained surfaces) and data-ds-particle-scale="hero" (15,000 points, production scale, for marketing-site Hero composition Variant E).

on-dark · preview scale

Usage rules

Hero only. The dome is the focal-moment animation — use it behind a primary marketing-site hero and nowhere else. Dropping it into content sections, data viz, or below-the-fold folds dilutes its signal and burns GPU continuously for a decorative element the reader has scrolled past.

Production scale is 15,000 points. Use data-ds-particle-scale="hero" on marketing pages. The preview scale (5,000 points) is for docs / contained surfaces only — it captures the breathing motion at a fraction of the GPU cost so the docs site stays responsive when this page is open.

Dark backdrop is non-negotiable. The dome reads as light particles glowing through space — that requires THREE.AdditiveBlending against a dark surface. A light-variant dome would need a different blend mode, different particle color, and a different visual identity — not the same component. Deferred to v2 of this primitive.

Reduced-motion: hold first frame. Users who've set prefers-reduced-motion: reduce see the dome at its starting state (size = base + amplitude, all phases at 0) with no animation. The visual signature is preserved; the motion isn't.

Pauses when offscreen. IntersectionObserver halts the render loop when the dome's container scrolls out of view. Resumes on re-entry. This is the same pattern .ds-marquee uses for tickers — saves CPU + battery on long pages where the dome sits in the hero.

Fallback for failed WebGL load. If Three.js fails to fetch (offline / blocked CDN / browser without WebGL), the container falls back to a subtle radial-gradient glow so the surface doesn't render as a flat black void. The [data-ds-particle-failed] attribute on the container triggers the fallback CSS.

Decorative, never interactive. The container has pointer-events: none — the dome never blocks clicks on UI behind it. The canvas carries aria-hidden="true" — screen readers skip it entirely.

Composes inside templates, not standalone. The dome is a positioned-absolute decoration behind content. Real usage: drop <div class="ds-particle-dome" data-ds-particle-dome data-ds-particle-scale="hero"></div> as the first child of a .ds-hero with position: relative, set z-index: 0 on it and z-index: 1 on the content. See Hero composition Variant E — Animated for the full pattern.

Performance notes

Three.js bundle ≈ 150 KB gzipped. Dynamically loaded on first .ds-particle-dome appearance — pages without the dome pay 0 KB. After first load, browser caches the CDN bundle indefinitely.

Device-pixel-ratio capped at 2×. On Retina displays the renderer caps DPR at 2 instead of using the device's actual ratio (often 3×). Visual difference is negligible at this particle density; frame-rate gain is real.

15K points × ~60fps measures comfortably on mid-tier laptops and recent phones. Older devices (4-year-old Android, low-end Chromebooks) throttle — the IntersectionObserver pause is the main mitigation; reduced-motion is the user opt-out.

The hidden 6 MB Lambda trap: compression and payload limits

When Postman lies and AWS rejects: a story about boundary measurement and the negotiation that happens too late.

Rohit Garg · Field note · 5 min

In this note

  • Problem
  • The Lambda boundary
  • Compression negotiation
  • The gotcha in testing
  • Fix
  • What changed
  • Production lesson

The problem. We were returning a 6.4 MB JSON blob from a Lambda function via API Gateway. The function ran clean, the response built clean, then API Gateway rejected the payload with a generic 500. Postman, locally proxying around API Gateway, returned the response just fine — so we shipped it. It only broke in production, and only intermittently.

The root cause turned out to be a boundary mismatch: Lambda's response limit is 6 MB raw, but API Gateway only negotiates compression after Lambda has already returned the payload. So the raw size check runs first, fails, and the gzip step that would have brought the blob to 1.8 MB never runs.

The fix was two-fold: gzip in the Lambda function itself before returning (using the runtime's compression library), and add a sanity check that returns a 413 with retry guidance when the raw payload exceeds 5.5 MB. The retry guidance points to a streaming endpoint we built for exactly this case.

Usage rules

Two cards is the sweet spot. Side-by-side compare reads cleanly. One card alone feels lonely; three+ cards on a row compress the rows too tight to scan.

Three row states. Default (neutral) for normal data. is-fail (orange tint + orange dot + orange text) for the row that broke. is-success (lifted neutral) for rows that completed under budget. Don't mix more than two states per card — the eye can only track so much state.

Progress bar can exceed 100%. Setting width: 106% on the fill bar signals overflow visually — the bar runs past its own track edge. Pair with is-fail rows to make the overflow narrative consistent.

Tick labels in the head row are mono-uppercase, max 3 words each. Pattern: <active label> on the left, <muted descriptor> on the right. Two ticks total — more and the head becomes a paragraph.

Use for technical / data-narrative content. Postmortem write-ups, performance comparisons, capacity diagrams. Not for marketing pages — the dot-grid + mono labels read as engineering, not pitch.

Usage rules

Alternate labels above / below the bar. Reading order goes left-to-right along the bar; above/below alternation keeps adjacent labels from crowding each other. Even-indexed milestones (1st / 3rd / 5th) go below; odd-indexed (2nd / 4th / 6th) go above. Or invert it — the pattern works either way as long as it alternates.

One segment per milestone. Segments are the visual rhythm; each one represents a chapter between two dates. 5–8 segments is the sweet spot. Below 5 the bar reads as too short for a roadmap; above 8 the labels start running into each other on tablet.

Default is 6 columns. Override via inline style="--cols: 5" on .ds-timeline-roadmap to change segment count. The grid keeps labels + segments aligned regardless.

One .is-active segment, always. Typically the rightmost ("we are here now"). The brand-orange anchor tells the user where the story currently sits. Multiple active segments dilute the signal.

Segments tint progressively brighter / darker. Left = oldest, dimmest. Right = newest, brightest. Reads as "history warming up to the present." The active segment overrides the tint with brand orange.

Mission heading is two-tone, not centered. Left-aligned heading with the opening assertion in default text colour and the qualifier in the muted second tone (--text-on-*-second). Centered headings work too but read more "section-opener" than "mission statement."

Milestone label = date + title, dashed underline. Date is mono-uppercase (subtle), title is Geist 14px with a dashed underline that mirrors a link affordance. In production, each title should link to a deeper page (blog post about the milestone, release notes, etc.).

Use for roadmap / company history / release-by-release. Not for changelog (use Carousel organism for inline release-notes), not for steps / workflow (use Lifecycle grid). The horizontal-bar metaphor reads as "journey through time" specifically.

Usage rules

Sits directly above the Footer. The Footer is brand + compliance chrome (formal). Pre-footer socials is the human invitation right before that ("come find us") — tone shift between the two surfaces is intentional.

4–6 tiles in the grid. 6 is the screenshot pattern (GitHub / Discord / X / YouTube / Docs / Blog). Fewer than 4 reads as a weak CTA strip — reach for the Footer's social icon row instead.

Centered heading, no eyebrow. Pattern consistent with the centered template variants: heading + short subtitle, nothing else above. The grid IS the chrome.

Each tile = one surface. Don't mix surface-types with categories (e.g. "Tutorials" alongside "GitHub"). The pattern is "where we live online" — one tile per platform / surface.

Meta is one line, <6 words. "3100+ Stars", "@videodb", "Workshops & demos" — numeric proof or short descriptor only.
